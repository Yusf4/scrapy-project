# Architecture

Two programs over two zones, orchestrated by Dagster. **Ingestion** (Scrapy) fills an immutable _landing zone_ — metadata in MongoDB, raw files in MinIO. **Transformation** derives a _curated zone_ — a new bucket and collection — by cleaning the landing data without ever modifying it. Dagster runs the two as monthly-partitioned assets (`landing_docs → curated_docs`) with a partition-to-partition dependency: a month's transform cannot run until that month's crawl has materialized and reconciled complete.

Identity is the **case URL** — the one field measured unique; the human-readable case number is not, since 7 of 60 sampled legacy records shared a number with a different document. Metadata records are one-per-URL and updatable (idempotency); landing _files_ are append-only under content-hash-versioned keys — changed content gets a new object, the old is never overwritten.

## Date partition size — monthly

The start/end range is sliced into per-tribunal monthly windows (`PARTITION_SIZE`, configurable; monthly implemented). The choice is second-order — total listing work is fixed by record density regardless of slicing — so it turns on overhead and retry cost. This source yields ~180–350 records/month at the busiest tribunal. **Daily** wastes an 810 KB request on each of thousands of empty days (small tribunals are empty for whole years); **yearly** pushes partitions past 270 listing pages and concentrates retry cost; **monthly** keeps ~18–35 pages per partition, retries ~1 minute (and re-downloads hash-skip anyway), and is a natural calendar unit. Density is per-source, so width is a knob, not a constant.

## Retries and rate limiting

Concurrency, timeout, and retry values are **measured against this server**, not defaults. A ramp showed throughput scaling cleanly to 8 in-flight requests and degrading beyond (~3× worse tail latency at 16), so `CONCURRENT_REQUESTS_PER_DOMAIN = 8`, AutoThrottle targeting 6 beneath it to adapt to live latency. The worst transient spike observed was 37 s, so `DOWNLOAD_TIMEOUT = 60` separates "slow but alive" from "dead". Retries use Scrapy's default taxonomy (5xx/408/429 and transport errors retried, 4xx not), `RETRY_TIMES = 3` — enough to survive transients given a measured sub-1% failure rate, retried requests deprioritised so one sick URL never stalls progress. The cap is _per process_; Dagster's `max_concurrent_runs: 1` stops two crawls multiplying it against the shared server. `robots.txt` disallows the case-document paths this project must fetch; the `ROBOTSTXT_OBEY=False` override is deliberate — these are public legal records and the target this project is built to collect, held under the measured caps above. Failed **document** downloads are logged (URL + reason) and the crawl continues; a failed **listing** page fails its whole (month × body) unit, since its contents are unknowable and per-record logging cannot substitute.

## Deduplication and idempotency

Re-running a range must not duplicate records or re-download unchanged files. Four layers: (1) Scrapy's dupefilter drops repeat requests within a run; (2) an atomic upsert on the unique-indexed URL keeps one record per case across runs (`$setOnInsert` first-seen facts, `$set` refreshable state, `$addToSet` the `bodies` set); (3) a SHA-256 **content fingerprint** — hashed after stripping HTML comments, because the server injects a per-request timing comment that makes raw hashing report every page as changed — skips unchanged content and writes changed content to a new hash-keyed object; (4) identical content at two URLs is caught by equal fingerprints. "Use the file hash to detect changes" is satisfied as _don't re-store_, not _don't re-download_: the HTML sends no ETag, so bytes must be fetched to be hashed (PDFs do send ETag — a parked conditional-GET optimisation). Completeness is enforced: the site states an exact count per query, each unit reconciles stored records against it, and Dagster refuses to materialize a month green unless every unit matches (failed documents ride along, individually logged).

## Scaling to 50+ sources

Configuration, process, and isolation change — not the architecture. The engine (partitioning, politeness, idempotent storage, reconciliation, orchestration) is source-agnostic and already in this code. Per-source splits into **data** — a registry entry (URL patterns, partition _strategy_ since a date filter is a per-source luxury, and politeness numbers) produced by a standardised onboarding recon (density survey, concurrency ramp, ETag probe, key-uniqueness sample, pagination, robots/ToS decision) — and **logic** — a small parser class contract-tested against stored fixtures, since extraction is judgment not config (JS-rendered sources swap in a browser downloader). Identity stays the URL. Sources run in parallel (independent politeness budgets) while each stays serial, each its own Dagster asset family so one outage isolates. Distribution across machines waits for a measured trigger — a crawl cycle exceeding its freshness window — since hardware multiplies breadth, not one source's polite depth, and keeps one control plane with distributed workers, never a second orchestrator. This project is a one-source instance of that design: parsers carry no framework coupling and source constants live in config — at 50 sources they are _named_, not invented.
